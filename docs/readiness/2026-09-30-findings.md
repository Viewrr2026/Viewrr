# Readiness findings — review branch

These changes are for staging review. They are not deployed to production and do not constitute an App Store readiness sign-off.

## Implemented in this branch

- Stripe Dashboard refunds now reconcile without requiring Viewrr refund metadata. Current Stripe refunds, transfer reversals and returned application fees populate the original payment's adjustment totals. Original invoice amounts remain intact. Duplicate deliveries converge on one refund record.
- Refund history is visible on invoices for both parties and on retainer cycles. Clients have a support email action for refund requests; requests do not automatically move money.
- Earnings and payment breakdowns account for actual transfer reversals and returned fees, without assuming a proportional fee refund.
- Payout updates read current Stripe status and update failure details. Available-balance notices read current Stripe balance. Copy distinguishes Stripe's paid status from independently confirmed bank arrival. The latest failed payout takes priority over an older paid payout.
- Project payment timeline access is restricted to the participants and does not expose admin-only events.
- Payment dialog can close on the card step. Payment entry is disabled before an invoice exists. Both roles get an invoice/history link. Final-delivery callout opens the delivery section rather than presenting inert actions.
- Accepted/declined/withdrawn one-off invitations are removed from pending lists. GBP icon replaces the dollar icon. External-link preview overlay is lighter and explains provider sign-in/access requirements; this is not a protected-file storage implementation.
- Versioned one-off estimates are beside project progress/description. Either participant can propose; the partner accepts, declines or requests changes. Invoicing uses agreed items/prices; changed items need another accepted version. Issuing is transactional and refuses duplicate invoices. Issued invoices and earlier estimates are retained. Existing projects without estimates retain their legacy invoicing path.
- For projects using estimates, unresolved terms block stage progression, and a final-stage submission requires an issued invoice. New one-off invitations require a single GBP provisional total. Acceptance records the project and agreed initial estimate atomically; repeated acceptance returns the same project. Older free-text budget invitations use explicit workspace estimates.
- Custom project stages already exist; corrected React Query draft loading so saved stage plans are available to edit.
- Retainer proposal history shows previous/revised fields, deliverables, prices, dates and terms. Whole-retainer estimate shows cycle structure, total invoiced, payments before refunds and scheduled remainder. Each cycle still has only one payable invoice. Premature pay instructions now reflect approval/invoice state. Expand/upload controls are explicit.
- Retainers continue using the shared payment ledger and central Stripe webhook, with cycle-specific acceptance, deadlines, one-cycle credit and access checks. Automated tests cover those rules. They are not converted to the one-off API, which would discard cycle context.
- Cached Accounts v1 policy errors can retry once with a stable compatibility key. Ambiguous network errors never change idempotency keys. Stripe Accounts v1 support still needs to be enabled for the relevant account if required.
- API logs no longer include response JSON. Privacy text corrects password hashing, lists operational providers, and removes unsupported current analytics/AI and fixed deletion claims. This is not a completed third-party SDK/privacy declaration audit.

## Staging procedure

1. Keep production unchanged. Verify the staging database is separate and Stripe credentials belong to the sandbox.
2. Apply migrations `0014_payment_adjustments.sql` and `0015_project_estimates.sql` after the existing migrations. Do not run schema push. The schema is additive; do not drop historical ledger/estimate data on rollback.
3. Deploy this review branch to staging. Platform webhook subscriptions must include `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled`, `charge.refunded`, `refund.created`, `refund.updated`, `refund.failed`, `transfer.reversed`, `application_fee.refunded`, plus the existing Connect/subscription events. Keep the existing signature verification and separate connected-account webhook secrets.
4. Existing Dashboard refunds need reconciliation. With staging DATABASE_URL and Stripe key set, run `node --import tsx script/reconcile-payment-refunds.ts` first (read-only). Inspect its payment IDs and refund amounts, then rerun with `--apply` to update Viewrr records. This command never requests money movement. Do not paste secrets into chat or logs.
5. Check both roles: partial/full refund history, adjusted earnings, invoice access, cancelled-checkout retry, close button, pending invitation filtering, estimate revision/acceptance/final invoice, custom stage editing and final delivery.
6. Check retainer upload environment parity: private storage configuration, FFmpeg including drawtext, ffprobe, custom-retainer flag and worker. Then manually complete proposal counter/acceptance, preview/revision/approval, cycle invoice, payment release and grace-period/freeze recovery. No external-link setting can substitute for protected original storage.
