# Readiness findings — review branch

These changes are for staging review. They are not deployed to production and do not constitute an App Store readiness sign-off.

## Implemented in this branch

- Stripe Dashboard refunds now reconcile without requiring Viewrr refund metadata. Current Stripe refunds, transfer reversals and returned application fees populate the original payment's adjustment totals. Original invoice amounts remain intact. Duplicate deliveries converge on one refund record.
- Refund history is visible on invoices for both parties and on retainer cycles. Clients have a support email action for refund requests; requests do not automatically move money.
- Earnings and payment breakdowns account for actual transfer reversals and returned fees, without assuming a proportional fee refund.
- Payout updates read current Stripe status and update failure details. Available-balance notices read current Stripe balance. Copy distinguishes Stripe's paid status from independently confirmed bank arrival. The latest failed payout takes priority over an older paid payout.
- Project payment timeline access is restricted to the participants and does not expose admin-only events.
- Payment dialog can close on the card step. Payment entry is disabled before an invoice exists. Both roles get an invoice/history link. Final-delivery callout opens the delivery section rather than presenting inert actions.
- Accepted/declined/withdrawn one-off invitations are removed from pending lists. GBP icon replaces the dollar icon. External-link preview overlay is lighter and explains provider sign-in/access requirements; this is not a protected-file storage implementation.
- Versioned one-off estimates are beside project progress/description. Either participant can propose; the partner accepts, declines or requests changes. Final invoices can revise wording and itemisation at the agreed total and VAT; changed totals or VAT need another accepted version. The issued invoice preserves its actual final line items and links back to the unchanged accepted estimate. Issuing is transactional and refuses duplicate invoices. Issued invoices and earlier estimates are retained. Existing projects without estimates retain their legacy invoicing path.
- For projects using estimates, unresolved terms block stage progression, and a final-stage submission requires an issued invoice. New one-off invitations require a single GBP provisional total. Acceptance records the project and agreed initial estimate atomically; repeated acceptance returns the same project. Older free-text budget invitations use explicit workspace estimates.
- Custom project stages already exist; corrected React Query draft loading so saved stage plans are available to edit.
- Retainer proposal history shows previous/revised fields, deliverables, prices, dates and terms. Whole-retainer estimate shows cycle structure, total invoiced, payments before refunds and scheduled remainder. Each cycle still has only one payable invoice. Premature pay instructions now reflect approval/invoice state. Expand/upload controls are explicit.
- Retainers continue using the shared payment ledger and central Stripe webhook, with cycle-specific acceptance, deadlines, one-cycle credit and access checks. Automated tests cover those rules. They are not converted to the one-off API, which would discard cycle context.
- Cached Accounts v1 policy errors can retry once with a stable compatibility key. Ambiguous network errors never change idempotency keys. Stripe Accounts v1 support still needs to be enabled for the relevant account if required.
- API logs no longer include response JSON. Privacy text corrects password hashing, lists operational providers, and removes unsupported current analytics/AI and fixed deletion claims. This is not a completed third-party SDK/privacy declaration audit.

## 9 October — interim retainer link delivery

- Retainer submissions now accept a delivery URL and note, using the existing deliverable_url column; no new migration or storage configuration is required.
- Links are validated as HTTP(S), without embedded credentials. The server does not fetch these URLs. Only the agreement's freelancer may submit, and existing schedule, acceptance and overdue-payment gates still apply.
- Clients can open links for review, request changes and approve each version. Retrying the identical pending submission does not duplicate it; resubmitting after requested changes creates a new version, including for the same hosted URL.
- Approval of all required items still creates one cycle invoice; only verified payment completes that cycle. Link delivery does not change the grace period or one-cycle credit limit.
- External links are available for review before payment. Viewrr cannot watermark, revoke, preserve immutable copies of, or protect originals hosted by another provider. Providers control access; freelancers should share preview copies when needed. Existing processed media retains its protected viewer/access checks.
- Direct uploads/R2 and retention policy remain deferred for a separate pre-submission decision. The manual retainer link-to-payment walkthrough is still required.

## 9 October — verified cycle success and retainer-wide reporting

- Custom overview uses all planned tasks/cycles, rather than legacy current-cycle counts: approved work and paid/approved cycles are separate measures.
- On-time cycle approval compares client acceptance with the agreed calendar end date in Europe/London. Overdue unapproved cycles count in the denominator; future unapproved cycles do not. Missing ratings display Not yet rated. Removed the fabricated relationship-health score from custom retainers.
- Payments received are shown before refunds, with successful refunds separately identified. Open requests are read from current records, including accepted/scheduled requests still outstanding.
- Custom history includes started/approved/paid cycle milestones, invoice amount/status, actual task counts and refunds. The paid state no longer disappears because the legacy history expected completed.
- Both participants receive a once-per-browser acknowledgement for a recent verified cycle payment, with a next-cycle navigation action. This does not unlock work early. Browser confirmation alone never triggers the success popup.
- Manual staging evidence: cycle 15 paid, four of seven whole-retainer deliverables approved, one of two cycles completed; cycle 16 remains scheduled for 19 October.

## 9 October — actionable agreement change requests

- Custom retainers route New Request to three focused choices: extra deliverables with an additional total price, revised cycle dates, or an early start after the previous cycle's verified payment.
- Requests produce an agreement version with current/proposed differences. The partner accepts, counters via the existing proposal editor, or declines. Decision history is visible. Pending requests do not change operational terms.
- Started, uninvoiced cycles permit appended deliverable groups with an increased price, preserving existing task IDs, submissions and approvals. Once fully approved/invoiced or paid, a cycle is immutable. Acceptance revalidates against work progressed since the request.
- Early starts can explicitly overlap the historical planned dates of an already-paid predecessor, without rewriting that paid cycle. No unaccepted initial proposal may use this exception. Existing payment/freeze and mutual-acceptance gates still apply.
- Retainer end-date extensions and unallocated dates require explicit acknowledgement in the request. Other overlaps are rejected.
- No migration required; uses existing versioned snapshots, decisions and notification records.

## 10 October — whole-retainer completion and notification delivery

- Final verified payment completes the custom agreement and its project only when all agreed cycles have approved work and verified ledger settlements, and no proposal is pending. Both parties retain invoice/refund/delivery history. Unfinished future cycles keep the retainer active. The worker also reconciles previously settled eligible agreements.
- Payout status notifications now use a durable event/recipient queue, deduplicated by payout ID/status; balance notices deduplicate by Stripe event. Retainer notices queue email and native push with project targeting and channel preferences.
- Email and push completion are recorded separately. Failed channels retry with backoff; accepted push devices are remembered across partial retries. Missing provider credentials leave delivery pending rather than falsely successful. Expo ticket acceptance is not proof the phone displayed a notification; an ambiguous network/process crash can still cause a repeated provider delivery (at-least-once delivery). Resend uses stable idempotency keys.
- Migration 0016_notification_delivery.sql must be applied before deployment. No historical push replay is performed; previously pending retainer emails retain their existing path. Deleted accounts have queue records removed.
